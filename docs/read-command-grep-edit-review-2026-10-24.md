# read / command / grep / edit 专项评审（2026-10-24）

**同日修复记录（包含 remote）**

下文保留修复前的评审和复现数据；生产代码现已完成对应修复。实现复用现有工具与批次调度，没有增加查询工具、持久化结果快照服务或额外模型总结调用。

- 本地与远端统一使用 `buildTextReadResult`、有界失败快照、UTF-16/UTF-8 编码恢复和 replaceAll 引擎；远端写回在目标机比较原始完整 SHA256，拒绝读取后发生的并发改写。远端 helper 错误码按统一前缀规则透传，批量读取不前进时明确失败。
- grep 按路径确定排序；移除会阻断后续页的累计原始 JSON 门槛；超长记录保留路径、行号和省略原因，游标不丢行。普通长行展示实际命中附近内容。已有 `maxMatches` 执行参数现在向模型开放，最多 200。
- 本地同阶段 edit 经现有多文件准备/提交/回滚引擎统一执行；回滚保留原始编码，检测到再次并发改写时不会覆盖外部修改。跨服务器远端文件仍各自提交，工具说明已明确此范围。
- replaceAll 以最多 50 个游标合并，不再逐命中分配记录；预先检查交叠和 32 MiB 结果上限，按源编码写回后再检查实际字节大小。
- 本地与远端批量泛读共享 64 KiB 正文预算，逐文件保留续读入口。显式 endLine 范围、tail 和内部上下文范围保持原单文件额度，避免拆碎已定位的函数。去重按实际返回范围建键，省略的文本不会被缓存成已发送。
- read reused 改为自闭合短回执；缺失路径向模型保留简短状态并阻断依赖阶段。本地读取有应用级 I/O 许可和排队取消，实际读取用限制读取兜底增长中的文件。
- 超过 32 MiB 的 UTF-8 日志可用 tailLines：只取末尾最多 128 KiB，再按现有预览额度返回；明确不可编辑、不提供绝对行号或编辑版本。两端共用同一 Go 展示函数，不整文件传输/哈希。
- command 保留独立滚动尾部，满前缀后仍更新实时预览，移交 service 时使用最近输出。两端输出缩减时均可返回日志；日志写入或关闭失败明确标 partial，不再误称 full，预览仍保留真实尾部。每日志原始输出最多 64 MiB，目录实行 128 文件/512 MiB 留存预算，活动日志不被淘汰；远端并发会话的目录预算为尽力协调，不承诺跨进程严格原子配额。
- 模型正文的 limit/head/tail 统一按 UTF-8 字节计，保留边界完整字符；完整日志不因预览缩减而丢失。

二次复查确认的三个边界也已修复：

- 共享 `EncodeLike` 在返回写入字节前重新解码，并逐字节比较编辑版本对应的规范文本。无 BOM UTF-16 修改后丢失识别特征、UTF-8 文本含 NUL 等无法忠实读回的结果，统一报 `E_EDIT_ENCODING`，本地/远端都在写入前拒绝，保留原文件。需要格式转换时须显式转为 UTF-8 或带 BOM 的 UTF-16；可正常识别的原编码继续保真写回。
- 单文件与批量模型 edit 共用带上下文的写入入口，取得文件锁后再次检查取消，全部文件准备完成后、首次提交前再检查一次。等待锁或准备期间取消的操作不写盘；已经开始的提交继续完成或回滚，避免半批中断。
- 远端日志在选择淘汰对象前，同时计入活动日志及新日志的字节和文件数预留。可通过淘汰已完成日志腾出空间时正常建日志；活动预留本身已用尽配额时直接拒绝，不误删仍有诊断价值的已完成日志。活动日志始终保留。

相应回归覆盖无 BOM 的 LE/BE 误识别、含 NUL 的两种解码分支、带 BOM 纯中文正常写回、单文件/批量等待锁时取消、编码失败后整批原文件保持不变，以及远端活动日志预留的字节/条数/无可用空间三种情形。等待锁的测试通过通道安排取消，不依赖 sleep。

结论：现有工具已经有较好的结果压缩基础，下一步收益主要来自可靠分页、保留有效诊断、消除重复回执和限制内部资源放大。继续一刀切降低输出上限，容易以漏读、重试和额外模型轮次抵消收益。

本次只做分析和临时探针验证，没有修改生产代码。基于当前工作区，已对照 `docs/tool-efficiency-review.md`，没有把其中已经完成的优化重新列成待办。下文的字节数均为 UTF-8 字节或明确标注的内存分配量，不等同于 token；单机合成数据不代表真实任务平均收益。

**1. 应保留的现有设计**

- UI 完整结果与模型精简结果分开；模型侧 read 使用带行号的文本块，edit 回执不重复发送整段 diff，command 不回显已经提交的命令和 cwd。
- read 每文件约 16 KiB 预览、20 文件批量请求、续读提示和截断行标记；会话级读缓存只比较实际载荷，历史压缩或重写后失效，写操作不会无谓清空缓存。
- command 模型侧保留首尾，超过模型预算时保留完整日志；超时移交原进程给 service，避免重新执行有副作用的命令或重复启动服务。
- edit 用版本约束修改、同一原始快照定位全部 changes、拒绝重叠和歧义；成功后返回新版本供后续编辑。小文件失败时附当前快照，避免额外 read。
- grep 在一次搜索里收集结果与统计，模型侧按文件分组展示，并保留路径、行号、分页和范围限制信息。

这些机制已经落地，不能把“增加去重、增加日志、不给模型完整 diff”当成新增收益。

**3. grep：优先修复分页，再优化输出量**

实现位置：`internal/tools/grep/grep.go:387` 的参数构造，`:478` 的 `sampleMatches`，`:695` 的续页处理；模型视图位于 `internal/app/infra_result.go:760`。

当前每一页都会启动新 rg，使用最多 4 线程，没有固定排序。offset 跳过的是本次搜索中先到达的命中行，而下一次搜索的到达顺序可以不同。这里即使工作区完全不变也会产生重复与遗漏；当前分页测试主要覆盖单文件，没有守住多目录并发遍历的边界。

低复杂度修法是让分页搜索按路径确定排序，文件内按行顺序前进。需要测量排序对吞吐的影响，不能只声称“线程数改成 1 就稳定”。更完整的方案是第一次搜索生成短期、有条数及字节上限的结果快照，后续按 cursor 读取；它能避免重复扫描，但需要处理工作区变更、快照失效和缓存预算，不建议在简单排序足够时立即引入。

第二个问题独立于排序：`maxGrepStdoutBytes` 统计的是**从进程起点开始的原始 JSON 总量**，不是这一页保留的结果大小；超过 10 MiB 后停止解析后面的 match，连 offset 跳过也无法继续计数。因此 offset 靠后的页可能永远取不到。探针生成 12,000 行、每行约 958 字节，显式指定 log.txt，offset=11,000 时得到：

    rows=0 matched=12000 next=0 truncated=true exhausted=false

2 MiB 单记录上限也会把整条匹配事件跳过，seen 随之少计。3 MiB 第一行加正常第二行的探针返回的是第 2 行、next-offset=1；这已经不能代表“返回了搜索流的前一条，下一页从第二条开始”。

建议把三件事拆开：是否保留正文、游标消费了几条、统计是否完整。分页行数以可定位的真实事件推进；无法保留的大记录必须给出明确原因和恢复方式，不能用 next-offset 假装全部结果仍可检索。不能仅提高 10 MiB 或 2 MiB 上限，问题会在更大输入上重现。

另外有三项实用优化：

- 默认预览始终取行首 500 字符，`parseMatch` 未利用 rg 的 submatches。命中若在长行后半段，grep 没显示命中，read 又只给该行前 2,000 字符，模型需要额外绕路。可在既有预算内优先显示命中附近的窗口，附列/字节位置与截断标记，完整源文件不变。
- 200 行达到后，当前仍在调用 `parseMatch`、JSON 解码、生成/裁剪文本，然后才检查 `sampleLimitReached`。可先判定“无需样本正文”，只处理必要事件；count 模式也无需构造每行文本。count 模式还可评估 rg 的专用计数输出路径，保持路径解析与精确统计可靠。
- `MaxMatches` 在执行结构中存在，但不向模型开放。一个简单的较小结果条数选项，可让“只找几个入口”的搜索少带大量无用行；需要区分仅找文件、找具体内容的收益，避免堆砌输出模式。精确总计目前意味着整棵树仍必须扫完，减少返回行数不会自动减少扫描时间。

**4. read：按有效信息节流，不按调用次数惩罚**

实现位置：`internal/app/orch_read.go:147` 的缓存键，`:309` 的去重，`:332` 的批量读取；`internal/app/infra_result.go:1023` 的 reused 回执；底层 `internal/tools/read/read.go:46`。

最容易直接改善的是 reused 回执。它现在固定重复一整段说明：正文不再发送、版本可用、需要文本可换范围。对小文件，说明比正文大得多。建议把通用契约留在工具说明中，回执只保留简短的“此范围已在历史中；版本是当前版本”。实际生成正文和 reused 两种候选时选更短的一个，同时保留版本及行范围。这里不需要更复杂的缓存。

同一路径范围的去重本身是正确方向，但请求键按原始参数组成，`默认读取`、`startLine=1`、显式全范围等有效结果相同的请求可能重复入库；重叠范围也不复用。可以先做**有效返回范围归一化**，减少等价请求漏命中。区间去重属于后续优化，必须保留文件版本、完整函数上下文和确实仍在历史中的证据，不能仅按 mtime 认为内容没变。

一次 read 的总预算可达约 320 KiB，多个 read 调用还可以在同阶段并发。建议增加批次级输出目标，初始可试验 48–64 KiB，但这是实验候选值，不是测出的最佳默认。注意：

- 小文件完整返回通常比为了省几 KB 拆成几轮更有效。
- 不要把一个明确请求的完整函数任意裁成碎片；能在当前调用返回时完整返回。
- 每个被收窄的文件都必须返回“已给出的范围、未给出的范围、当前版本和续读入口”，不能静默丢弃 files 后半部分。
- 若预算在模型渲染后才收窄，读缓存只能记录真正送入历史的内容，不能缓存被省略的正文。
- 把所有未见内容都自动接着读完，会把预算控制变成额外往返；续读应由任务需要决定。

read 的 dedup 只省模型输出，不省磁盘成本。范围读取仍先整文件读入、解码、规范化、计数并哈希；缓存命中也走这条路径。大文件反复读局部或 tail，会重复 O(文件大小) 工作。建议保持“编辑快照”路径严格，另给超大日志提供不可编辑的流式范围/tail；没有全局行索引时明确使用字节/尾部相对位置，不能伪造可用于 edit 的全局行号和版本。这样 command 提供的完整日志超过 32 MiB 后仍能被诊断。

可靠性还有两个边界：

- 当前先 Stat 再 os.ReadFile，文件在两者之间增长时实际读取量仍可能超过限制。可以 open 后 f.Stat，并用上限加 1 的限制读取作为最终兜底；同时拒绝非普通文件，避免管道等无结束输入。
- read 的批量路径没有 ctx，内部还建立独立并发池。外层最多 16 个工具、每个批量内部最多 16 个文件读取时，理论上可放大为 256 个同时读取。可传递取消信号、在读取/解码/哈希阶段检查，使用共享 I/O 许可或总在途字节预算。只是每层各自有限，不等于整个应用的资源开销合理。

缺失路径和目录现在被整体过滤。探针读取唯一不存在的文件，得到 files=0，但 `toolStageSucceeded` 判为成功。可以继续在 UI 隐藏预期缺失项，但模型结果最好保留简短逐路径状态，让依赖阶段判断“必要输入是否拿到”。这是可观测性/契约取舍，不应伪装成读取成功。

**5. command：压缩预览必须有可靠的恢复通路**

实现位置：`internal/app/orch_file_ops.go:579` 的执行，`:664` 的更新判定，`:800` 的日志收尾，`:908` 的日志创建；`internal/app/infra_bridges.go:68` 的捕获缓冲；`internal/app/infra_output_encoding.go:63` 的编码检查。

优先处理“full 日志是否真的完整”：创建日志、写前缀、后续写入及 Close 存在被忽略的错误。关闭 spill 句柄模拟写失败后，工具仍返回 nil 写错误和 full 路径，但真正的最后错误已经丢失。这会让模型依据残缺证据判断成功或找错原因。

建议为日志维护累计字节、已持久化字节、首个写入错误和完整性状态。失败时继续排空子进程输出，避免让捕获故障堵住命令；另用内存滚动尾部保留最新诊断。full 只能表示完整可读副本，否则明确 partial/complete=false，说明丢失原因。不能建议重跑有副作用的命令来恢复输出。

当前内存是固定前缀，达到 128 KiB 后不会再增长。流式更新按 Len 变化触发，所以输出在继续、预览却不再变化；`promoteTo` 又把这个旧前缀播种给 service，超时前最新 ready/error 可能没有进入服务的初始尾部。建议保留固定首部和独立滚动尾部，用累计写入序号决定是否推送；服务已有 RollingBuffer，可复用相同语义。最终首尾模型预览依然保留，不需要扩大返回量。

完整日志本身还没有总磁盘预算，只在启动时清理选中工作区中超过 24 小时的文件。长时间运行、多工作区和高频命令不能靠这个形成结构性上限。应有每文件、文件数量及总字节预算，清理只针对明确的 Ally 日志、避开当前写入文件；触及上限时明确降级，不再声称 full。日志压缩后的恢复通路必须继续可用。

命令结束后 `fileIsUTF8` 会扫描整份日志，再决定是否转码。大 UTF-8 日志通常无需重读，可在捕获时增量验证编码，保留跨块的未完成字符，仅确需转码时重扫。CPU 时间仍与字节数相关，但能减少一次完整磁盘读取和退出后的等待。

上下文方面，不建议默认只保留最后几行或让 LLM 总结每条命令。构建/测试的决定性错误可能位于中间，LLM 总结还增加延迟与失败路径。可评估有界的确定性诊断摘录，同时始终保留退出码、实际首尾、完整性状态及可检索路径；诊断规则未覆盖的命令回退现有预览。

**6. edit：先堵住写入和内存放大，再考虑省几个回执 token**

实现位置：`internal/app/orch_edit.go:101`、`:117`、`:175`；纯算法 `internal/tools/edit/apply.go:500`、`:630`；阶段调度 `internal/app/orch_tool_stages.go:74`。

UTF-16 问题来自读取阶段先转成 UTF-8，写入阶段仅恢复换行和 UTF-8 BOM，不保留源编码。探针原始字节为：

    ff fe 61 00 0d 00 0a 00

将 a 改为 b 后落盘为：

    62 0d 0a

这个例子中的文字仍正确，但文件格式发生未声明改变，依赖 UTF-16 的下游程序可能失败。prepared.before 同样是解码字节，批次回滚也缺少原始编码副本。建议让读取快照携带原始字节或可还原表示、解码文本、源编码、BOM 与换行信息；写入及回滚按原编码恢复，版本/哈希口径在 read、edit、远端之间保持一致。若暂时不支持保真写回，应明确标记不可编辑，不能静默转换。

replaceAll 的注释称不保留每个命中，实际循环仍逐一 append locatedChange，随后全局排序。Windows/amd64、i5-12600KF 上的一次性基准：

| 命中数 | 输入字节 | 时间 | B/op |
|---:|---:|---:|---:|
| 10,000 | 20,000 | 0.81 ms | 1,863,544 |
| 100,000 | 200,000 | 7.81 ms | 22,426,464 |
| 1,000,000 | 2,000,000 | 105.20 ms | 217,558,952 |

B/op 是一次操作累计分配量，不是峰值常驻内存；时间是合成单次采样，不应作为稳定性能承诺。这里足以证明“没有逐命中存储”的注释不符合实现。

建议单 replaceAll 使用计数加流式构建快路径；多 change 的场景可按已排序迭代器合并命中并检查交叠，或至少对命中记录数量建立明确预算，不能通过删除交叠校验换性能。对输出长度用安全算术预估，在 Grow、生成 diff 和写盘前执行统一的结果大小限制。探针仅用 8,192 个 a，将每个 a 换成 4,097 个 b，就成功写出 33,562,624 字节，而后续 read 因超过 32 MiB 拒绝打开；更大的放大还可能耗尽内存。

跨文件约定也需要对齐。单个 edit 内部支持多文件准备和尽力回滚，但模型每个调用只传一个文件；主调度器分别执行同阶段调用，并明确“失败不回滚已完成工作”。探针同阶段提交两个 edit，a 版本正确、b 版本过期，结果为：

    a.ok=true b.error=E_VERSION_MISMATCH a.disk="new\n" b.disk="old\n"

因此当前不是 AGENTS.md 所述的跨文件原子校验/批次写入。需要按约定在编排层聚合同阶段本地 edit，完成统一准备、版本检查和提交；不能把单文件 rename 原子性当成跨文件事务，也不能依赖单元测试里直接调用内部多文件函数来证明模型入口具有该保证。跨文件回滚依然是尽力而为，不能宣称能抵御任意进程崩溃或外部并发改写。

还有一些较低优先级的可靠性改善：提交前已有完整 SHA256 却只比较 6 位版本，可以用完整哈希比较内部快照；短 token 是 30 bit，扩长会增加少量上下文但可降低碰撞风险，应作为版本协议整体评估。写入工具目前忽略 Chmod/Sync 错误，若要求严格权限或持久化保证，应分别处理，不应无条件报告成功。二次哈希仍无法消除“校验结束到 rename 之间外部程序改写”的窗口，需要明确进程内锁的保证范围。

edit 的模型侧结果已经很小，不建议新增大段 diff 或每次附变更后全文。小文件失败快照应保留；大文件可以在错误位置已确定时返回有界的相关候选/范围和当前版本，减少无效重读，但不要靠模糊匹配静默扩大修改区域。

**7. 累计上下文的优化口径**

每个工具结果只写入历史一次，但之后仍会参与后续模型输入。一段结果若占 T 个 token，后续还有 R 次请求，它带来的逻辑累计输入量约为 T×R；这不是实际计费量，供应商前缀缓存、折扣和压缩都会影响成本。缓存命中也不意味着历史内容不占上下文窗口。

因此应优先减少“高体积、长期停留、对后续无贡献”的新结果，并减少失败后的额外模型轮次。不要为了统计上少输出一次，就把完整函数拆成多次 read、删除命令诊断或让搜索静默漏结果。

建议记录无内容的工具元数据：工具名、持续时间、结果原始字节、模型字节、估算 token、截断类型、read 去重命中及实际省下的量、日志完整性、分页是否推进、错误码。验收应覆盖：

- 真实任务完成率及最终测试结果；
- 总模型轮次、工具调用次数、重读/重试次数和耗时；
- 追加的工具结果 token、累计模型输入、供应商已缓存输入；
- 工具 p50/p95 延迟、累计分配/峰值内存、磁盘占用；
- 所有裁剪内容是否有明确、有效、不会重复执行副作用的恢复通路。

command 的 12 KiB 命名还需要先统一：`compactTextForModel` 最终按 rune 数裁剪，read 和 grep 部分预算按字节，日志头尾又按字节。12,288 个中文字的命令结果实测 36,895 字节且未裁剪。因此“12K 输出”的前后对比必须先说明单位，不能直接宣称 token 节省百分比。

所有优化应尽量发生在新工具结果加入历史之前，保持历史前缀稳定。不要每轮回写旧 read/grep/command 消息；现有显式 compact 是另外一条协议，已经会使相应前缀缓存失效，不能把其成本混入普通工具优化。
