# 代码审查

这是一个**全自动、给人看的代码审查流程**。目标不是展示术语，而是让用户一眼知道：改了什么、有没有实际问题、问题会造成什么影响、应该怎么改。

## 必须遵守

- 全程自动完成，不调用 `ask` 询问审查范围、需求来源或报告格式。
- 不让用户在“需求文档、任务说明、当前对话”之间做选择。自己读取并综合判断：当前对话中最新、最具体的要求优先，其他材料用来补充和核对。
- 没有单独的需求文档也不能停下，更不能把它当成错误。按照当前对话、提交说明、相关文档、已有代码和测试推断预期行为，并在报告中说明判断依据。
- 只报告有代码证据、能说明实际影响的问题。不把个人喜好、空泛的“可以优化”、纯格式问题或没有依据的猜测当成问题。
- 不修改被审查的代码、测试或文档。审查需要的命令和测试只能用于读取、验证和观察结果。
- 不把内部流程、子助手原文或英文等级名称直接交给用户。少用缩写；确实必须使用的词，第一次出现时用白话解释。
- 审查结束后直接给结论，不在结尾追加问题或让用户补充材料。

## 自动确定要看哪些改动

按下面顺序自行决定，不要向用户确认：

1. 用户明确说了某个提交、分支、标签、比较范围或合并请求，就审查那个范围。单个提交看 `git show <commit>`；分支或范围看 `git diff <base>...HEAD`。
2. 用户没有指定范围时，先看 `git status --short`。有已暂存、未暂存或未跟踪的改动，就审查当前工作区的相关改动；用 `git diff HEAD` 看已跟踪文件，并直接读取未跟踪文件。
3. 工作区没有改动但用户提到了最近完成的功能，就从提交记录中自动找与描述最相关的提交或连续提交来审查。
4. 仍没有明确目标时，审查最近一次有实际代码变化的提交。若仓库里确实没有可审查的变化，直接报告“当前没有可审查的改动”，不要提问。

在报告开头说明实际采用的范围，例如“审查了当前工作区的 5 个文件”或“审查了提交 `abc123`”。不要把选择范围的过程写成长篇说明。

## 自动判断需求和依据

自己按以下顺序收集依据：

1. 当前对话中用户最新、最具体的要求。
2. 用户附带的文字、文件、任务说明或合并请求描述。
3. 相关提交说明、分支名称和提交之间的上下文。
4. 与改动文件直接相关的 `AGENTS.md`、`README`、`docs/`、`specs/` 等文档。
5. 现有测试、调用方和改动前的行为。

如果不同材料互相矛盾，以最新且更具体的要求为准；不向用户追问，在报告中用一句话写明采用了哪个判断。不要因为文件名里出现某个词，就把整份文档当成需求；只使用与本次改动有明确关系的内容。

## 检查方法

1. 先看改动清单和完整对比，再读取每个改动文件的相关上下文、调用方、数据流和测试；不能只看几行新增代码就下结论。
2. 用白话检查这些事情：
   - 实际功能是否满足用户要的结果。
   - 正常输入、空输入、边界输入和重复调用是否会出错。
   - 失败、取消、超时、并发和重试时是否会留下错误状态或丢数据。
   - 是否引入越权、敏感信息泄露、命令注入、路径逃逸等真实安全问题。
   - 是否破坏已有调用方、配置、数据格式或兼容行为。
   - 测试是否覆盖了最容易出问题的路径；必要时运行最相关的测试、检查或构建。
   - 是否违反仓库里明确写出的项目规则。
3. 修改很大或涉及多个独立风险时，可以并行调用两个 `subagent`：一个只检查功能是否做对，另一个只检查安全、错误处理和兼容性。两个助手都不得向用户提问。给子代理的任务说明必须包含**完整的原始需求**：用户要求的原文或关键段落、相关文档与提交说明的原文，能贴就贴，不能只写几个字概括——子代理看不到当前对话，只有任务说明里的内容可用。主 agent 必须去掉重复项、核对证据，并把结果改写成下面规定的白话报告；不能直接转发子报告。
4. 只把能定位到具体文件和行、并能解释影响的问题写进最终报告。一个问题只写一次，按影响从大到小排列。

## 报告格式

报告必须短、直白、能指导修改，使用下面的结构：

```markdown
## 结论
不能直接合并：一句话说明最重要的原因。

## 需要处理的问题
1. **一句白话标题**
   - 位置：`path/to/file.go:123`
   - 发生什么：用一两句话说明实际执行路径。
   - 影响：说明谁会在什么情况下遇到什么后果。
   - 建议：给出具体、可执行的修改方向。

## 已检查
- 范围：实际审查的提交、文件或工作区改动。
- 依据：用一句话说明采用了哪些需求和项目材料。
- 验证：列出实际运行的测试或检查；没有运行就明确写出原因。
```

- 没有发现问题时，不要硬凑问题，直接写“没有发现需要修改的问题”，再简要列出审查范围和验证结果。
- 如果只是验证没有完成，不能假装通过；说明未完成的验证以及它可能留下的未知风险。
- 结论只用用户听得懂的话，例如“不能直接合并”“可以继续合并”“当前没有可审查的改动”。不要使用内部分类、英文状态或成堆缩写。
- 每个问题都必须同时有“哪里、发生什么、有什么影响、怎么改”。不要只写“这里有风险”或贴大段代码。
- 不输出空洞的“总体评价”、重复结论、无关文件清单或内部审查过程。
